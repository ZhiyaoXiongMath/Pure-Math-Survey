# 2.4.1 持久化开发规范

本文件规定开发者在跨聊天、跨机器和多轮 PR 中如何保持一致。它不是安装 skill 每次运行应读取的内容。

## 1. 唯一入口与权威

- 根 `AGENTS.md` 只做短入口，指向本目录；保留当前仓库中无关的有效规则。
- 产品合同：[DEVELOPMENT_GUIDE.zh-CN.md](DEVELOPMENT_GUIDE.zh-CN.md)。
- 阶段边界：[PR_WORKFLOW.zh-CN.md](PR_WORKFLOW.zh-CN.md)。
- 唯一进度：[DEVELOPMENT_STATE.yaml](DEVELOPMENT_STATE.yaml)。
- 可复制操作模板：[CHAT_PROMPTS.zh-CN.md](CHAT_PROMPTS.zh-CN.md)。
- 来源与已观察基线：[BASELINE_AND_SOURCES.zh-CN.md](BASELINE_AND_SOURCES.zh-CN.md)。

用户后续明确修订优先。旧 r4/r5、四模式和审核开发指南不自动重新生效。首次开发将旧 CONTRACT/STATUS 标为历史并给出新指针；不维护两份当前状态，不另建 HANDOFF、progress、todo 三套账本。

## 2. 开始工作

每个新聊天先读 AGENTS、STATE、本文件和当前 PR 的任务范围。首次接手或合同发生变化时再完整读指南。查询真实 GitHub 状态后再修改：main、活跃分支、现有 PR、前序是否已 merged、当前 HEAD 的检查和审查。

主分支已经变化是需要比较的事实，不是自动重启项目的理由。已有同阶段分支或 PR 应续用；已有用户授权无需再次询问。不能把技能指令或自己的计划当成用户尚未给出的发布授权。

初始设计包交付时只获设计任务授权。后续按用户实际发送的指令执行，并在 STATE 更新授权快照；模板本身不授予权限。

## 3. 范围与实现习惯

围绕当前仓库做最小足够的改动。复用现有 canonical 存储、路径安全、原子写入、TeX 导出/编译和打包基础；不建立替代仓库、第二套 CLI、数据库服务、任务调度器或新的长审计协议。

本版硬边界：只有 minimal；取消运行审核和强制子聊天；知识与文章同源；只有选定模块的简短方法及组合；未支持模式明确拒绝；来源、条件和版本不伪造。不要为维持旧测试而恢复已取消功能。

用户说“轻量化”指每篇运行少消耗。开发规范可以详细，但它们不进安装包，不在每次知识抽取时全量加载。运行 SKILL 及适配指令只保留必要规则。

## 4. 修改知识合同和格式

源论文决定数学；rules.v22 决定写作；2.4.1 适配决定取消哪些流程。更改数学表达必须回到节点正文，派生文件由程序生成；禁止多份互不一致的陈述。

原始 rules 冻结，hash 见指南。发现条款需要改进，先记录具体歧义与建议，由用户明确修改要求后再升规则版本；本版开发不擅自改成 v23，更不能把某篇论文的答案/节点名单写进通用规则。

guide 的适配表允许本轮已明确授权的取消审核，这是新需求覆盖旧流程，不是无权豁免数学准确性。

## 5. 一个 PR 的完成方式

形成实现 → 跑相关检查 → 更新 STATE 的已知事实 → 提交并创建 PR → 独立 review → 修具体问题并补审 → 合并。

PR 描述只写问题、改动、结果、实际验证和已知限制，引用当前阶段要求。不要粘贴整份指南或把未来阶段说成已完成。每阶段形成一个主 PR，常规修正继续该 PR。

审查者不同时编写同一实现。审查范围是当前差异和风险；有具体缺陷给出文件位置、影响和最小修复建议。没有缺陷也说明检查边界。不用形容词或分数替代证据。

只有实际执行的检查才记录 pass；not_run、blocked 和 skipped 如实保留。外部 CI 不可用时可以完成本地检查与具体 PR，说明待完成项；不能将未知状态写绿。

## 6. 检查应当有限

只运行解决具体风险或现有必要 CI 所需的检查。保留路径安全、原子写入、schema 拒绝、原字节导出、旧项目不变、安装资源及构建等有效检查。删除四模式/审核协议已取消的正向要求，替换为不支持时明确拒绝。

不为文案修改跑完整数学项目；不要求每条 rule 对应一项单元测试；不反复启动相同的全套检查。开发样例一旦有效且相关内容未变，后续复用，变更只补测受影响部分。

构建成功不等于数学正确；安装通过不等于真实读者理解；一个样例通过不等于所有文章都正确。这些边界用简短准确文字说明，不变成新的运行审核门禁。

## 7. STATE 更新原则

STATE 写计划、已确认事实、实际证据、阻碍和下一动作。它不复制整个讨论过程，历史以 Git commit 和 PR 为准。

建议在以下事件更新：开始阶段、任务边界确实改变、出现实际阻碍、形成候选、下一阶段登记前序 merge。工具每返回一条日志无需改 STATE。

当前 PR 不记录自身最终 commit SHA，不提前标 merged。当前 HEAD 和审查结果从 GitHub 读；下一阶段记前序 merge。已经检查过的较早 commit 可以按其实际值记录，但必须注明它不是当前自动有效的证据。

STATE 允许暂时保留 ready_for_review，而 GitHub 实际已 merged；新会话先对账、继续下一阶段，在下一次正常提交中补记。最后发布也是同理，不为追求状态文件瞬时同步新增空 PR。

## 8. 合并、冲突、中断及重试

- 执行合并前重新确认实际 HEAD 与有效检查/审查适用范围；若使用 API，传 expected HEAD，拒绝竞态。
- 用户已明确授权本阶段合并或发布时，条件满足后直接完成；没有授权时交付具体候选供最后决定，不提前停止在抽象计划。
- 冲突按当前合同解决，不能用整体覆盖丢掉他人改动或恢复旧审查链；解决后只补验受影响部分。
- 不对 main force push，不改历史 tag，不删除无关分支。需要破坏性动作时另依实际用户授权处理。
- 超时或未知结果先查询远端对象，再决定重试；不能重复创建 PR、重复发布或另开同阶段替代分支。
- 中断恢复先读现有文件、差异及 PR。局部已完成成果保留，不因为换聊天就重做来源研究。

## 9. 安装与隐私边界

开发文档、完整转写、聊天记录、开发 STATE 与真实私有数学材料不在安装资源 allowlist。公开仓库只提交本任务需要的中性设计摘要；完整私人讨论不随本包分发，也不额外公开提交。

rules 原文在 PR-01 曾暂存于本开发目录；PR-04 起唯一权威文件为 [references/rules.v22.txt](../../../skills/pure-math-survey/references/rules.v22.txt)，保持原始字节。安装只包含当前模式、简短 KB/运行合同、原始 rules 和实际依赖脚本/样式。

数学来源可读取不等于可以随安装包再分发。保留来源定位即可，不新增长许可审核表。已有旧项目和历史证据不改写。

## 10. 最后一条交接

每轮给出可执行的下一步，而非笼统“继续”：哪个阶段、哪个实际 PR、当前是开发/修正/审查/待合并/发布、先读哪些文件、应在何处停止。

聊天里的交接是 STATE 与 GitHub 实况的当次摘要，不是第二个永久状态源。所有新聊天仍须重新读取实际 HEAD，不能把摘要当永久许可或永远有效的验证。
