# Pure-Math-Survey 2.4.1：分阶段 PR 与交接

设计日期：2026-10-21。以下 PR 编号均为**工作阶段 ID**，不是 GitHub PR 号码；实际实施进度见唯一 DEVELOPMENT_STATE.yaml，并重新查询 GitHub。

## 1. 推进方式

按 **开发当前阶段 → 形成一个可审查 PR → 有限独立 review → 必要修正 → 合并 → 下一阶段** 推进。不要求一个聊天把整个版本全部实现。

开发期 review 检查软件改动和本阶段产品结果；它不会进入用户以后运行 skill 的链路。每个阶段正常只做一次独立审查，有具体修正时补审变化及受影响行为，不按固定次数循环。

审查者从被审 PR 的实际 head_sha 读取本阶段规范与 STATE；PR-01 新增文件尚未在 main，不能默认从 main 找它们。实现内容变化后的补审仍由独立审查者完成，不把作者自查当成独立结论。

默认从最新 main 创建当前阶段分支。前序 PR 已合并才进入下一阶段，不维护五条同时开发的长期分支。示例分支名 `v2.4.1/pr01-contract`，实际分支/PR 以查询到的对象为准，已有同阶段工作必须续用。

## 2. 五个阶段总览

| 阶段 | 目的 | 合并时应成立的事实 |
| --- | --- | --- |
| PR-01 | 固定合同和持久化交接 | 仓库中有唯一 2.4.1 设计、规则适配、进度与启动入口；运行代码仍为原版 |
| PR-02 | 只开放 minimal，解除运行审核 | 当前候选能从建库到文章准备/构建/打包，不要求审核记录或子聊天；其他模式被明确拒绝 |
| PR-03 | 建立同源轻量 KB | 可独立交付小单元及连接；Minimal 使用同一份陈述；不再强制快慢两套内容 |
| PR-04 | 按 rules.v22 成文和排版 | 真实样例满足六页、概念/主贡献/模块/图要求；同源导出可靠 |
| PR-05 | 集成、安装及发行准备 | 2.4.1 候选安装包可用，当前文档/资源/版本一致；真实发布另以 Release 事实确认 |

阶段必须形成可运行的中间状态。若 PR-02 解除审核与 PR-03 的一个机械数据变更不可分，允许把该必要部分前移并在同一 STATE 记录原因；不能合入坏掉的半条链路，也不为了凑五个 PR 制造空 PR。任务总范围不扩大。

## 3. PR-01：开发合同与持久化入口

### 范围

- 将本包 `docs/development/v2.4.1/` 中的指南、PR 流程、开发规范、STATE、聊天提示及基线资料纳入仓库。
- 原始 `rules.v22.txt` 在本阶段放在 `docs/development/v2.4.1/rules.v22.txt`，逐字节保存；不加载到旧安装，也不宣称旧模板已符合它。
- 创建或增补根 `AGENTS.md`，内容见本包片段；先核实当前是否已存在，保留无关规范。
- 在旧 `docs/development/CONTRACT.md`、`STATUS.md` 开头加简短说明：旧内容是 2.1.0 历史，本版以 2.4.1 文件为准；旧事实不重写。
- STATE 填实际 base、分支、阶段状态；不编造 PR number、review、测试或最终 HEAD。

本阶段只提交设计及导航，禁止把未实现的 2.4.1 宣传为当前版本。完整私人转写不入公开仓库；`BASELINE_AND_SOURCES` 已保存必要的中性需求摘要和时间定位。

### 有限检查

核对路径/链接、rules hash、文件间术语与目标一致。若现有 CI 自动执行，读取结果即可；不手动跑论文生成或整个旧数学审核任务。

### 交接终点

创建 PR-01，交付实际 URL、变更摘要、具体检查及审查提示。没有已授予的合并授权时，等待用户操作或明确授权；**不要只交付本地计划而不形成授权范围内的 PR**。PR-01 合并后再开始 PR-02。

## 4. PR-02：minimal-only 与取消运行审核

### 范围

- 更新 SKILL/metadata/README 的候选运行说明；默认当前会话，不固定 Astra/ultra，不强制 create_thread、controller/worker 或非作者。
- 统一缩减 CLI、profile 枚举、计划读取器和公开功能；Thematic/Lecture/Paper 与非 integrated views 返回明确 unsupported，禁止静默降级。
- 解除 inventory、load_project、readiness、prepare、verify_generated、snapshot、package/release 整个调用链中的 review 凭据依赖。
- 删除活跃的 review/readiness 审核功能；可以保留明确拒绝旧命令的短兼容诊断，不能保留后台可偷偷运行的审核工作流。
- 同步最小安装资源清单及受影响测试，主分支候选仍能安装和运行。
- 建立 `references/minimal-runtime.md`：单会话流程、取消审核的适配规则、必要机械检查、结果状态。可先在文档中说明 PR-04 尚将落实 v22 排版，不声称本阶段已经全部满足。

### 过渡合同

本阶段尚未完成新 KB 表达和 v22 模板。用 `2.4.1-dev.2` 标识候选，并使用独立的过渡 policy（例如 `minimal-transition-pr02`），不能复用 r5 身份而改变意义。新建项目必须有 `runtime_contract: minimal-lean-2.4.1`，先在任何写入前拒绝缺少该合同的旧项目；旧 schema 仅可作为当前候选新生成数据的临时实现细节。

此阶段允许保留少量旧格式的机械容器，但不得要求模型继续撰写 fast/slow 长稿、review 内容或证明承诺。若容器本身妨碍目标，将其必要简化从 PR-03 前移并记录。阶段样例不是正式用户迁移服务，最终 schema 由 PR-03 固定。

### 验收

1. 一个小型合成项目，无 reviewer 工具、无审核目录、无 accepted 记录，能走通候选 minimal 的必要链路。
2. 其他模式、旧命令、旧项目和非法路径有清晰诊断；失败不改原文件。
3. 源码/安装内容中无可达的强制派工、审核放行及其自动加载链。允许历史目录和拒绝诊断含相关词，不能仅靠全文禁词 grep 判断通过。
4. 当前安装的已有安全写入、TeX 字面保存、打包机制没有因取消审核而失效。

### 禁止替代实现

不能写虚假的 accepted records；不能把审阅函数统一改成 return True；不能拿 `--draft` 作为常规轻量路线；不能另建一个第二套 skill 避开原代码。

## 5. PR-03：轻量知识单元与直接复用

### 范围

- 固定新 KB schema `3.0.0`、output schema `3.0.0`；替换过渡容器，按指南第 5 节保留最小字段和文件。
- 复用 JSON frontmatter、canonical LaTeX、稳定 N-/S- ID、sources 和安全写入；去掉快慢双份正文、强制 overview/discovery/coverage/reviews。
- 实现 sources/conventions/nodes/routes 与短索引；类型、作用、重要性候选分开。
- 结果原字节导出；独立导出补齐实际需要的概念定义和记号；保存来源定位。
- 更新/重复 prepare 只重生成派生片段，保留作者写过的引导、连接排版和已交付旧输出。
- 明确新旧 schema 行为；不开发自动迁移器、不篡改旧库、不做智能全领域去重。

候选版本 `2.4.1-dev.3`。成文可暂用清楚标识的过渡模板；不宣称已满足 PR-04 的六页最终版式。

### 验收

用一个小型、可复用的合成 fixture 验证：概念依赖导出、一个多前提连接、一个备选连接、一个独立分支、缺失引用诊断。再验证一次 canonical 改动传递到文稿、再次 prepare 不覆盖作者内容。

只建库路径必须真的结束于 KB，不创建稿件/PDF，不要求页数或审核记录。`importance.level=null` 可以正常交付，不以等待人工评分阻塞。

## 6. PR-04：rules.v22 写作、图和版式

### 范围

- 将 PR-01 保存的 rules **移动**到 `skills/pure-math-survey/references/rules.v22.txt`；保持 hash，更新引用、安装 allowlist，避免留两份可分别修改的权威副本。
- SKILL 在写作时先加载简短适配再读原始 rules。只建库不必读所有排版条款。
- 发布候选政策改为最终 `minimal-rules-v22-lean-2.4.1`，候选版本 `2.4.1-dev.4`。
- 用最终三节模板、完整而简短的模块接口、核心概念自然复用、相邻来源、自动编号、无描述性标题落实写作要求。
- 11pt、≥20mm 边距、图实质文字≥10.5pt、六页正文、参考文献新页；不加入运行时视觉审核。
- routes、正文引用和 TikZ 的节点/连接共用同一身份；需要时修改图排版，而非另造一张内容不同的图。
- 默认本地编译 PDF；TeX-only 不谎报实测页数；编译/超页只允许有界局部修复。

### 一次实际内容验收

选择一个固定版本的真实数学来源，明确题目、版本、文件/URL 和约定范围。优先复用合法的现有材料；不得声称当前设计包已经附带某篇论文原文。若样例私有，使用本地证据或可授权访问的链接，不提交私人原文、聊天或完整转写。

由本 PR review 在有限范围内同时查看最终 KB 和 Minimal：核心概念被定义且使用，主要贡献无约定范围内遗漏，关键模块不臃肿、条件明确，图的主要组合与正文一致；看最终 PDF 页面检查模板排版。复用同一份验收结果，不另开“数学审核流水线”。若指出具体缺陷，只修并补看相应部分。

这一样例是本版开发验证，不是普遍正确性证明，也不授权在每次用户运行增加同样的 reviewer。一个真实样例与已有合成 fixture 足以构成本阶段基线；额外样例须解决具体剩余风险。

## 7. PR-05：发行候选、安装包和成本事实

### 范围

- 清除安装包里旧模式模板、旧审核/dispatch 指令和不再可达脚本；旧内容留 Git 历史即可。
- 同步双语 README、SKILL metadata、帮助、版本输出、Release notes、resource manifest/checksums；目标版本为 `2.4.1`。
- 复用现有打包工具，验证干净目录解压安装、资源完整性、KB-only 与 minimal 的实际入口。
- 保留并运行现有 Linux Python 3.10/3.12、Windows Python 3.12 中受改动影响的工程检查；删除无支持功能的旧 4×5 正向要求，不删仍有效的路径/写入/安装保护。
- 复用 PR-04 的内容样例，不无故重做全文抽取与数学 review；最终安装差异只跑相关 smoke。
- 记录真正可取得的耗时、token 和加载文件。没有可比旧数据时不声称百分比改善，不为获取对照去重跑昂贵旧审核流程。

### 交付候选

应得到实际候选 `pure-math-survey-2.4.1.zip` 及 `.sha256`，与仓库内容一致。GitHub 自动 Source code ZIP 不代替安装 ZIP。检查结果绑定实际构建输入；最后修补后按受影响范围重建。

只有用户已经授权发布时才创建 tag/Release/上传附件；否则提交具体候选供最后决定。不能提前写 released。阶段 PR 的 merge 与正式发布是两个不同事实。

### 合并后和发布时

最终候选应从最终实际合并提交构建或核对其安装树与已验证输入一致；出现相关代码/资源变化才补测。发布后核实 Release 指向、非 prerelease 状态（如请求正式发行）、两份安装附件及校验值。

STATE 不必为写入“我刚刚发布了”再造一个修改当前最终 SHA 的补丁循环。GitHub Release 是发布事实；下一次正常维护再把它登记入 STATE 即可。

## 8. 每个新聊天怎么恢复

新执行者按以下顺序恢复，而非依赖上次聊天的记忆：

1. 读根 AGENTS、`DEVELOPMENT_STATE.yaml`、开发规范；首次接手读开发指南，此后只读当前阶段相关段落。
2. 查实际仓库默认分支、main HEAD、STATE 里的活跃分支/PR（若有）及对应 checks/reviews/merge。遇到 null 字段，搜索同阶段现有分支或 PR，不自行假造号码。
3. 核对记录是否滞后，并判断当前动作是开发、修正、审查、等待用户合并、已合并转下一步，还是发布准备。
4. 在现有授权范围内完成该动作，更新唯一 STATE 的已知事实与剩余事项。只在权限确实欠缺或范围无法确定时询问。

| 实际状态 | 必须采取的动作 |
| --- | --- |
| 当前 PR 尚未创建，但已有分支/提交 | 接续现有工作，不重启同阶段 |
| PR open，检查失败或有具体 review 缺陷 | 修当前 PR，先解决真正问题 |
| PR open，当前 HEAD 尚未有效审查 | 交给独立审查者检查该 HEAD |
| 审查后新增提交 | 补审变化及受影响行为；旧结论不能自动覆盖新内容 |
| PR 已可合并且用户授权已存在 | 核对预期 HEAD 后执行授权合并，不重复索取许可 |
| PR 已可合并但用户保留手工合并 | 给出具体 PR 和合并提示；不替用户合并 |
| PR merged | 以真实 merge SHA 确认前序完成，开始下一阶段 |
| PR closed 但未 merged | 记录阻塞及原因，不能跳到下一阶段 |
| main 出现新改动 | 比较相关影响、同步或解决冲突；只补测受影响行为 |
| 全部阶段 merged，但没有正式 Release | 报告开发完成、尚未发布，并按授权推进发布 |

合并方式沿用用户选择或仓库现有方式，不强制 squash/rebase。无论何种方式，记录 GitHub 返回的实际 merge SHA，不能假设它等于开发分支 HEAD。删除已合并开发分支不会丢失已合并提交历史，但本流程不自动处理无关分支。

## 9. STATE 与 GitHub 的关系

`DEVELOPMENT_STATE.yaml` 是唯一持久化开发进度/下一步记录。GitHub 是当前 HEAD、checks、review、merge 和 Release 的实时事实来源。二者允许出现“文件尚未记录刚刚合并”的短暂差异；新聊天必须先对账。

**当前 PR 的文件不填写它自己的最终 commit SHA，不在合并前声称自己已合并。** 把 SHA 写进该提交本身会改变 SHA。STATE 可以记观察到的 base、前序 merge SHA、既有证据 URL。

作者在最后代码提交中把状态写为 `ready_for_review`，后续审查直接留在 GitHub/聊天实际证据中。不要为把 ready_to_merge 或 reviewer 的新 HEAD 再写入 STATE 而制造无意义提交。

下一阶段 PR 顺带登记前序 merge。最终阶段的 `next_action` 使用条件句：若仍 open，完成审查/合并；若 merged，核实发行；若 Release 已存在，报告真实结果。这比机械的“PR-05 后再做一个更新状态 PR”更简洁。

## 10. 每轮结束的交接内容

最终消息只需六项：本阶段做了什么；实际分支/PR URL；做过哪些相关检查及未做项；具体缺陷或阻碍；STATE 路径；下一聊天可复制提示。

下一提示必须包含仓库、当前阶段和真实 PR URL（已有时），要求重新查询实际 HEAD。不得使用“上一聊天已通过所以直接合并”、固定旧 HEAD 或“自动完成所有后续 PR”。提示模板在 [CHAT_PROMPTS.zh-CN.md](CHAT_PROMPTS.zh-CN.md)。
